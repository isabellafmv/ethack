# PHSI Pipeline — заметки по технической реализации

Реализованы Step 2 (Database Build) и Step 3 (Math & Normalization) из мастер-плана.
Step 4 (LLM PDF PoC) и Step 5 (Bonus Portfolio) — следующие, см. "Что дальше".

## Запуск

```bash
pip install sqlalchemy pandas numpy
python3 pipeline/build_database.py   # пересобирает sp500_sustainability.db с нуля
python3 pipeline/scoring.py          # считает PHSI, пишет в таблицу phsi_scores, печатает сводку
```

Оба скрипта идемпотентны — можно перезапускать сколько угодно раз, старые данные
затираются, а не накапливаются.

Технический нюанс: SQLite не пишется/не читается напрямую в этой примонтированной
папке (`disk I/O error` — типичное поведение SQLite на bridged/FUSE-подобной ФС).
Оба скрипта поэтому работают с локальной копией в `~/.phsi_build/` и синхронизируют
готовый `.db` обратно сюда в конце. Если будете переносить пайплайн на "чистую" машину
или в облако — это ограничение, скорее всего, снимается само собой.

## Структура

```
pipeline/
  db_models.py       — SQLAlchemy ORM: companies / esg_ratings / financials / phsi_scores
  build_database.py  — Step 2: загрузка CSV + прагматичный штраф для ESG + запись в БД
  scoring.py          — Step 3: winsorize → sector z-score → блендинг весов → sensitivity sweep
data/
  financials_demo22.csv — финансовые рычаги, вручную собранные (см. ниже, почему вручную)
sp500_sustainability.db — результат, таблицы: companies (503), esg_ratings (503),
                           financials (22, демо), phsi_scores (22 × 3 варианта весов)
```

## Покрытие данных

- **ESG (Sustainalytics, через Kaggle CSV) — все 503 компании.** Это уже независимый
  агентский рейтинг, не декларация самих компаний — см. обсуждение в чате, отдельное
  второе агентство (MSCI/CDP) не потребовалось.
- **Финансовые рычаги — демо-подвыборка 22 компании (2 на каждый из 11 GICS-секторов).**
  Bulk-доступ к Yahoo Finance API / SEC EDGAR / Wikipedia заблокирован сетевой политикой
  окружения (403 на уровне шлюза — проверено и с Mac через мост, и из облака). Данные
  собраны точечно через stockanalysis.com (revenue, gross profit, net income, FCF, capex,
  market cap за последний отчётный год). Это ровно тот сценарий, который мы обсуждали:
  для институционального клиента (Bloomberg/Refinitiv/FactSet-подписка) это решается
  заменой одного источника на bulk-API — код `scoring.py` от этого не зависит, он
  работает с любым источником, который положит данные в те же колонки `financials`.

## Методологические решения (зафиксированные в чате)

1. **Нормализация — sector-relative**, не универсальная: z-score внутри GICS-сектора,
   и для финансовых рычагов, и для ESG-компонент. Иначе utilities/energy систематически
   штрафуются за структурно высокий Capex, а software — за структурно низкую маржу.
2. **Прагматичный штраф** применяется одинаково к обоим блокам: пропуск = 75-й перцентиль
   ХУДШЕГО направления по сектору (не медиана). Для ESG — 100 из 503 компаний были
   доимпутированы. Для финансов — банки (USB), REIT (VICI, SPG) и utilities (XEL, SO)
   структурно не публикуют Gross Profit / классический Capex — это не ошибка данных,
   а особенность бизнес-модели, и штраф отражает это как "низкую прозрачность",
   осознанно, а не занижает их незаслуженно.
3. **Winsorization на 5-м/95-м перцентиле по всей выборке** перед сектор-z-score —
   например, у Western Digital net margin 71.88% в последнем финансовом году
   (разовая история, не операционная норма), обрезается до P95 перед сравнением.
4. **Веса 60/40 + sensitivity sweep (50/50, 70/30)** считаются одновременно и хранятся
   в одной таблице `phsi_scores` — топ-5/боттом-5 стабильны на реальных 22 компаниях
   (см. вывод `scoring.py`), но это стоит перепроверить на полном покрытии.

## Известное ограничение демо, о котором стоит сказать на защите прямо

При n=2 компании на сектор z-score внутри пары почти всегда бинарный (одна компания
"выигрывает" по метрике, другая получает 0) — отсюда, например, PSX (Energy) внизу
рейтинга с financial_subscore=0, хотя это крупная прибыльная компания: просто у SLB
чуть лучше по каждой метрике в этой конкретной паре. Это статистический артефакт
демо-выборки, а не суждение о качестве компании — снимается на полном покрытии
(503 компании на сектор — десятки, а не 2). Явно скажите это на защите, чтобы жюри
не приняло это за баг методологии.

## Data-quality находка

В исходном CSV у `BF.B` (Brown-Forman) была полностью пустая строка (Sector, Industry,
все ESG-поля — NaN), похоже скрейпер Kaggle-датасета не справился с тикером с точкой в
названии. Sector вручную восстановлен (Consumer Defensive, Beverages — публичная
информация), ESG-поля получили обычный прагматичный штраф. Задокументировано в коде
(`build_database.py`, функция `load_esg`).
